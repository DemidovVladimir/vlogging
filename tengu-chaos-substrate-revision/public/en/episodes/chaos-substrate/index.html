03 / KEYED BY ITS INPUT

Every result is keyed
by its own input

The key is the hash of exactly what a result is made from. The Merkle tree turned out to be unnecessary.

InputKeyWhat is savedAfter editing pack()
unit pack(): code + a header with path and linesSHA-256(header + code)vector, 768 numbers≠ new vector
file budget.rs: its bytesSHA-256(file bytes)parse: units, links≠ parsed again
feature summary: its textSHA-256(model + text)summary vector= from storage
chaos 1.1 · Merkle tree

a summary keyed by the hash of all its feature’s files → 4 summaries redone

chaos 1.2 · its own input

a summary keyed by the hash of its text → 0 summaries redone

A vector is stored under the hash of its unit: its code plus a header with path and lines. Same hash: the vector still fits.

Keys as in the chaos 1.2 code. The 1.1 and 1.2 numbers: one code snapshot, one edit, measured 27.10.2026 (scene 04). Merkle tree: Ralph Merkle, 1979. stateRoot and light clients: ethereum.org.

chaos add compares file hashes and redoes only the difference.

The same edit with chaos 1.1 on the same code: 4 summaries redone, 6 features changed, links 3,954 → 3,952 (an add bug, found while removing the tree and fixed in 1.2). Why not file times or git diff: switching branches and back gives a file a new time with the same code, and git does not know what the index saw last time.

08 / TENGU / TAKEAWAY

Read less.
Trust what you can check.

  1. Index once. Run add after every edit. Ask with feature.
  2. Key each result by its own input. A tree is for checking without the data.
  3. A hash proves “the same”, not “correct”.

Routing by meaning can miss, and links between repositories need exact names.

Built by a senior AI/ML engineer: agentic systems and LLMOps, 10+ years in production software; Rust, TypeScript, Python.
