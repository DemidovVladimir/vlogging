# TENGU EP.03 — Режиссёрский план

Задача: зритель может найти реальную точку TLS-проверки и понять, почему отзыв CA ещё не гарантирует защиту приложения. Подробность повышена по просьбе автора.

## 00 / Заставка — 00:00–00:03

[Запустить MP4 со звуком. Дать закончиться заставке, затем перейти к 01.]

## 01 / Ключ доверия. Четыре. — 00:03–00:41

eMudhra: не взлом шифра, а провал ключей и доставки защиты.

- 01: Один из закрытых ключей промежуточного CA — число 4.
- 02: Отзыв сертификатов не обновляет автоматически каждый клиент.

Срез на 22.10.2026. Пост с «RSA PRIVATE KEY» — мем, не формат реального ключа.

## 02 / Сертификат — делегированное доверие — 00:41–01:29

Сервер присылает цепочку. Клиент проверяет её до своего доверенного корня.

- 01: Корень — исходная точка доверия клиента, не подарок от сервера.
- 02: Подпись корня разрешает промежуточному CA выпускать сертификаты.
- 03: Клиент проверяет путь и имя сервера. Отзыв и CT — дополнительные проверки.

Упрощённый путь. CA = удостоверяющий центр. api.example.com — условный адрес.

## 03 / Большая кривая. Крошечный секрет. — 01:29–02:17

Q = d × G: открытый ключ Q вычисляется из секретного числа d.

- 01: При нормальной генерации d выбирается непредсказуемо из огромного диапазона.
- 02: Здесь все восемь секретов оказались меньше 256.
- 03: Сравнение публичных ключей раскрывает слабый секрет. P-384 при этом не «взломали».

× — умножение точки кривой на число. Схема, не программа восстановления ключей.

## 04 / Подписали не тот набор ключей — 02:17–02:55

Предварительная версия eMudhra: ошибка процедуры, затем ошибка выбора.

- 01: CA сообщает о дополнительном наборе после изменения процедуры wrap/unwrap.
- 02: По версии CA, похожие метки привели к выбору слабых ключей для CSR.
- 03: Подпись сертификата закрепила ошибку. Причина появления слабых чисел ещё не установлена окончательно.

CSR — запрос на сертификат с открытым ключом. Не утверждаем, что доказана неисправность HSM.

## 05 / Один ключ. Две цепочки. — 02:55–03:44

Cross-signing: разные сертификаты подтверждают один и тот же открытый ключ.

- 01: Слева — путь через emSign.
- 02: Справа — cross-sign от Sectigo: другой сертификат, тот же ключ.
- 03: Убрать один путь недостаточно, если клиент ещё принимает другой.
- 04: Блокировка по SPKI охватывает сертификаты с этим открытым ключом.

Показан один из TLS-ключей. SPKI — структура открытого ключа; блокируется её хеш.

## 06 / Подмена сервера, не машина времени — 03:44–04:35

Опасность возникает, когда клиент принимает поддельную идентичность сервера.

- 01: Обычная сессия: клиент проверяет сервер и согласует ключи шифрования.
- 02: Для подмены нужны и сертификат, и возможность направить соединение к атакующему.
- 03: Если клиент принимает подделку, посредник может читать и менять передаваемые данные.
- 04: Один ключ CA не расшифровывает задним числом записанный трафик с forward secrecy.

Модель угроз, не демонстрация атаки. Forward secrecy — защита прошлых сессий при последующей утечке долгосрочного ключа.

## 07 / Подпись, отзыв и CT — разные проверки — 04:35–05:32

Одна корректная цепочка не гарантирует, что сертификат будет принят.

- 01: Подпись отвечает: соответствует ли сертификат ключу издателя?
- 02: CRL / OCSP и локальные списки сообщают об отзыве — если клиент их применяет.
- 03: CT требует подписанные подтверждения от журналов: SCT. Это не проверка CRL.
- 04: Для этого инцидента CT и экстренные блокировки закрывали путь в браузерах; другие клиенты могли отстать.

Google: до блокировки не было TLS-сертификатов этих CA в CT. CRLSet — не полный список всех отзывов.

## 08 / Одна macOS. Не одна система доверия. — 05:32–06:23

Проверяет сертификат конкретная TLS-библиотека с конкретной конфигурацией.

- 01: Обновление системной политики защищает клиентов, которые её используют.
- 02: PEM-файл — набор сертификатов, не автоматическая доставка отзывов.
- 03: Название curl не определяет поведение: важны сборка, backend и выбранное хранилище.

Наблюдение для встроенного CLI-пути из incident guide на 22.10.2026. Не утверждение обо всех версиях macOS/curl.

## 09 / Исправление должно дойти до процесса — 06:23–07:11

Зависимость обновлена ≠ контейнер пересобран ≠ новый процесс запущен.

- 01: Go добавил denylist в crypto/x509. Обновить toolchain — лишь первый шаг.
- 02: Исправленный код должен попасть в новую сборку приложения.
- 03: После развёртывания проверяем реальный процесс, включая HTTP-инструменты агента.

Версии Go — первые исправленные ветки из advisory, не рекомендация навсегда. Пост otomir23 о колонке не подтверждён независимо.

## 10 / Тестируем отказ, а не просто ошибку — 07:11–07:59

Один клиент. Обе цепочки. Без отключения проверки сертификата.

- 01: Используем контролируемые тестовые endpoints из incident guide.
- 02: Нужен отказ именно проверки сертификата, а не любой сетевой сбой.
- 03: Проверка двух маршрутов не заменяет тест всех затронутых CA и всех приложений.

Команды не выполняются этой страницей. Не использовать -k / --insecure. Тестовый сервис видит обычный запрос.

## 11 / Закрыть риск, не отключая защиту — 07:59–08:42

Клиенту — актуальная проверка. Владельцу сайта — рабочая доверенная цепочка.

- 01: Составьте карту клиентов: браузеры, CLI, runtimes, контейнеры, устройства.
- 02: Обновление должно изменить именно тот verifier или bundle, который используется.
- 03: Необновляемые системы требуют изоляции и плана замены; сайтам может потребоваться перевыпуск.

Удаление корня может ломать незатронутые сайты и не закрыть альтернативную цепочку. Решения согласуйте с владельцем инфраструктуры.

## 12 / Доверие нужно доставлять — 08:42–09:02

Секрет — непредсказуемый. Проверка — актуальная. Исправление — в работающем клиенте.

- 01: Надёжный алгоритм не исправляет плохую генерацию ключей.
- 02: Правильный отзыв не помогает клиенту, который его не применяет.
- 03: Проверяйте не «компьютер вообще», а каждое реальное соединение.
