## 01 / Браузер блокирует. А приложение?

[R; затем → по смысловым фазам, не по таймеру.]

Браузер отклоняет опасный сертификат, а сервис на том же компьютере устанавливает соединение. Шифрование включено в обоих случаях. Различается проверка того, кто находится на другом конце.

В истории eMudhra это не теоретический вопрос. Восстановили закрытые ключи промежуточных удостоверяющих центров — тех, кто может заверять сертификаты сайтов. Здесь разберём не только саму ошибку: почему отзыв не доходит до всех клиентов, что сделала Cloudflare и как довести исправление до работающего приложения. **Начнём с причины.**

## 02 / P-384. А секрет — меньше 256.

[R; затем → по смысловым фазам, не по таймеру.]

У этих ключей использовалась кривая P-384. Но секретные числа оказались меньше двухсот пятидесяти шести. Вместо непредсказуемого значения — всего двести пятьдесят пять ненулевых кандидатов. Открытый ключ уже есть в сертификате, поэтому результат можно проверить. Один из восстановленных секретов вообще равнялся четырём.

Предварительное объяснение самого CA — ошибка в процедуре генерации: для сертификатов выбрали не тот набор ключей. Детали ещё расследуются, поэтому объявлять сломанным криптографический модуль нельзя.

Последствие конкретное: чужой человек может создать подпись, которую математическая проверка признает верной. **И эта подпись может опираться не на один путь доверия.**

## 03 / Два сертификата. Один опасный ключ.

[R; затем → по смысловым фазам, не по таймеру.]

У затронутых ключей были и сертификаты eMudhra, и перекрёстные сертификаты через Sectigo. На экране меняется издатель сертификата, но сам открытый ключ остаётся прежним.

Почему это важно? Удаление одного пути не доказывает, что клиент отвергнет альтернативный. Нужно учитывать, каким корням он доверяет и какие цепочки умеет построить.

Блокировка по отпечатку SPKI адресует именно ключ: другой сертификат с тем же ключом тоже не пройдёт. Такой подход использует защита Chrome. Это не повод удалять весь корень Sectigo наугад: он обслуживает и другие сертификаты. **А что атакующему даёт оставшийся путь?**

## 04 / Шифрование есть. Собеседник — не тот.

[R; затем → по смысловым фазам, не по таймеру.]

Допустим, атакующий уже может перехватить соединение. Он показывает сертификат с нужным именем и подписью скомпрометированного центра. Если приложение принимает его, оно устанавливает защищённое соединение не с тем участником.

Посредник может отдельно соединиться с настоящим сервисом. Получаются два зашифрованных канала, а между ними — тот, кто читает и меняет данные. Поэтому «у нас же HTTPS» здесь недостаточно.

Это не означает, что ключ центра открывает все старые записи трафика. При прямой секретности прошлые сеансовые ключи из него не восстанавливаются. **Решающий вопрос сейчас другой: почему приложение вообще приняло подделку?**

## 05 / Один сертификат. Две проверки.

[R; затем → по смысловым фазам, не по таймеру.]

Правильная подпись не означает, что ключу всё ещё можно доверять. В Chrome здесь сработали разные механизмы. Certificate Transparency требует подтверждений от публичных журналов. До блокировки сертификатов сайтов от этих TLS-центров там не было, поэтому клиенты с обязательной CT уже не принимали бы такие подделки. Затем CRLSet доставил прямую блокировку ключей.

У серверной программы может быть другой набор проверок: цепочка и имя сайта проходят, а нужной блокировки или CT нет. Публикация списка отзыва центром ещё не означает, что программа скачает и применит его.

**Поэтому инфраструктурному провайдеру пришлось исправлять не только браузерную сторону.**

## 06 / Что исправляла Cloudflare

[R; затем → по смысловым фазам, не по таймеру.]

Cloudflare обновляла проверку исходящих соединений: от прокси к origin и от приложений к API. Исправила общие хранилища доверия и образы, затем активировала изменения перезапусками и развёртываниями. Защита CDN и серверной части Zero Trust была развёрнута двадцатого октября.

Для cloudflared вышла версия 2026.10.2. **Но почему недостаточно просто установить обновление?**

## 07 / Исправление должно попасть в работающий процесс

[R; затем → по смысловым фазам, не по таймеру.]

Возьмём Go. В crypto/x509 добавили блокировку затронутых ключей. Исправления есть в версиях 1.26.10 и 1.27.3. Но обновление компилятора на машине сборки не меняет уже развёрнутый бинарник. Чтобы получить именно эту защиту, сервис нужно пересобрать и развернуть заново.

Это не значит, что любой старый бинарник обязательно уязвим: на результат влияют и другие проверки. Мы показываем доставку конкретного исправления.

У другого приложения путь может отличаться: системное хранилище, отдельный CA-файл, встроенная библиотека. Например, даже curl выбирает хранилище в зависимости от сборки и настроек. Нужно установить, что использует именно ваш процесс. **И проверить результат, а не галочку в списке обновлений.**

## 08 / Проверяйте путь доверия. Не только замочек.

[R; затем → по смысловым фазам, не по таймеру.]

Для проверки используйте актуальные рекомендации поставщика и тестовые цепочки из материалов инцидента. Нужен отказ именно проверки сертификата, а не таймаут или ошибка DNS. Рядом нужен обычный корректный HTTPS-запрос: он должен продолжать работать.

Проверять следует из того же runtime, с тем же хранилищем и сетевым маршрутом, что у рабочего сервиса. Иначе вы проверили соседнюю программу, а не свою.

Главный вывод: криптографическая подпись, решение о доверии и доставка обновления — три разных механизма. В eMudhra сломался ключ. А масштаб проблемы определило то, сколько программ продолжало ему доверять.
